# MassSpecGym v1.5 Acquisition and PySirius Pre-Picked-Spectrum Import

Research for issue #6 (child of #2). Fact-finding only — no design decisions.

## 1. MassSpecGym v1.5 acquisition

**Finding: MassSpecGym v1.5 is sourced directly from the HuggingFace Hub dataset repo `roman-bushuiev/MassSpecGym`, config `main`, at the file `data/MassSpecGym1.5.tsv`. There is no HF dataset *revision*/git-tag/commit pin in use anywhere in the reference material — the "v1.5" pin is entirely encoded in the filename inside that one dataset repo, which hosts both v1 and v1.5 files side by side.**

- This repo's sibling project reads it with pandas directly via the `hf://` filesystem protocol:
  ```python
  df = pd.read_csv("hf://datasets/roman-bushuiev/MassSpecGym/data/MassSpecGym1.5.tsv", sep="\t")
  ```
  (`external/ms2mol-evaluation/src/ms2mol_evaluation/evaluation.py`, `Evaluation._load_massspecgym`, decorated `@Cache()`). No `revision=` argument, no `huggingface_hub.hf_hub_download(..., revision=...)` call — the `hf://` fsspec path resolves against the `main` branch of the dataset repo at call time. No `external/ms2mol-evaluation/src/ms2mol_evaluation/constants/urls.py` or `.../data/` module exists in the checked-out repo (glob returned no matches) — `_load_massspecgym` is the sole source of the URL/dataset id/version in the reference material.
- The HuggingFace dataset card (`https://huggingface.co/datasets/roman-bushuiev/MassSpecGym`, fetched via the HF API on 2026-09-17) confirms:
  - Dataset id: `roman-bushuiev/MassSpecGym`.
  - `configs: - config_name: main, data_files: [{split: val, path: data/MassSpecGym1.5.tsv}]` — i.e. the dataset card itself currently wires the `main` HF `datasets`-library config to `MassSpecGym1.5.tsv`, meaning even the "default" load via the `datasets`/`massspecgym` Python libraries resolves to v1.5's file, not v1's.
  - A section titled **"MassSpecGym v1.5 update"** states v1.5 "addresses several evaluation pitfalls identified in the 'MassSpecGym in the Wild' audit" and lists the new/changed files it adds to the *same* dataset repo: `data/MassSpecGym1.5.tsv` (main dataset; schema identical to v1, but `smiles` re-standardized with `rdkit.Chem.MolToSmiles(canonical=True)` instead of PubChem-standardized SMILES used in v1), `data/auxiliary/MassSpecGym1.5.mgf` (MGF export of the same data), `data/molecules/MassSpecGym1.5_retrieval_candidates_mass.json`, `data/molecules/MassSpecGym1.5_retrieval_candidates_formula.json`, `data/molecules/MassSpecGym1.5_pretraining_molecules_2.5M_tani070.txt`, `data/molecules/MassSpecGym1.5_pretraining_molecules_50M_tani070.txt`, and a corrected-description-only file `data/molecules/MassSpecGym_molecules_MCES2_disjoint_with_test_fold_4M.tsv`.
  - Related papers: MassSpecGym NeurIPS 2024 paper (arXiv 2410.23326) and "MassSpecGym in the Wild" (arXiv 2606.19624, the paper that motivated the v1.5 corrections). GitHub companion library: `pluskal-lab/MassSpecGym` (not vendored in this repo).
- Columns of `data/MassSpecGym1.5.tsv` (confirmed via the HF `datasets-server` `first-rows` API for `roman-bushuiev/MassSpecGym`, config `main`, split `val`, and matching exactly what `Evaluation._load_massspecgym`/`_to_spectrum` in `evaluation.py` consume):
  1. `identifier` (string, e.g. `MassSpecGymID0000001`)
  2. `mzs` (string: comma-separated peak m/z list)
  3. `intensities` (string: comma-separated peak intensity list, same order as `mzs`)
  4. `smiles` (string, RDKit-canonicalized in v1.5)
  5. `inchikey` (string, full InChIKey)
  6. `formula` (string, neutral molecular formula)
  7. `precursor_formula` (string, ionized/precursor formula)
  8. `parent_mass` (float64)
  9. `precursor_mz` (float64)
  10. `adduct` (string, e.g. `[M+H]+`)
  11. `instrument_type` (string: `Orbitrap` or `QTOF`, per `SiriusEvaluation._split_orbitrap_qtof`)
  12. `collision_energy` (float64)
  13. `fold` (string, e.g. `train`/`val`/`test`)
  14. `simulation_challenge` (bool)

**Uncertainty / gap:** the dataset card's "MassSpecGym v1.5 update" section documents the *files* added for v1.5 but not a formal HF *dataset-repo commit hash* that should be pinned for reproducibility. Because `configs.main.data_files` on the dataset card already points at `MassSpecGym1.5.tsv`, and because `hf://…` reads resolve against the live `main` branch, a caller who wants a byte-for-byte reproducible pull (rather than "whatever `MassSpecGym1.5.tsv` currently contains on `main`") would need to separately capture/pin an HF repo commit sha — no such mechanism is used anywhere in the current reference material. This repo's own `pyproject.toml` dependency on `huggingface-hub` is consistent with, but does not by itself confirm, any particular pinning strategy — no code in this repo (only in the *external* sibling packages) currently calls `huggingface_hub` APIs for MassSpecGym.

## 2. PySirius pre-picked-spectrum import

**Finding: PySirius supports importing an already-picked, feature-level spectrum list (e.g. an MGF where each entry is one MS2 feature with known precursor mass/charge) via `ProjectsApi.import_preprocessed_data_as_job` (or its synchronous sibling `import_preprocessed_data`), and this endpoint's signature carries no peak-picking/feature-detection parameters, in contrast to the mzML/mzXML endpoint which requires such parameters. This is the exact call already used by `metabolite_annotator.tools.sirius.sirius_config.Sirius.import_spectra`.**

- `external/metabolite-annotator/src/metabolite_annotator/tools/sirius/sirius_config.py:73-80` (`Sirius.import_spectra`):
  ```python
  import_job = self.api.projects().import_preprocessed_data_as_job(
      self.project_info.project_id,
      input_files=[str(spectra_file.resolve())],
  )
  self.api.wait_for_job_completion(self.project_info, import_job)
  ```
- The generated client documents this endpoint (`external/sirius-client-openAPI/client-api_python/generated/docs/ProjectsApi.md`, `import_preprocessed_data_as_job` section, endpoint `POST /api/projects/{projectId}/import/preprocessed-data-files-job`) as: *"Import ms/ms data from the given format into the specified project-space as background job. Possible formats: ms, mgf, cef, msp."* Parameters: `project_id`, `input_files` (list of file paths/bytes), `ignore_formulas` (bool, default `False`), `allow_ms1_only` (bool, default `True`), `opt_fields`. **No peak-picking/feature-detection parameters exist on this call.**
- By contrast, `import_ms_run_data(_as_job)` (`POST /api/projects/{projectId}/import/ms-data-files(-job)`, same docs file, "Import and align full MS runs from various formats into the specified project. Possible formats: mzML, mzXML.") **requires** a `parameters: LcmsSubmissionParameters` argument. `external/sirius-client-openAPI/client-api_python/generated/PySirius/models/lcms_submission_parameters.py:24-34` shows this model carries explicit feature-detection/peak-picking knobs: `align_lcms_runs` (bool, whether to align LC/MS runs), `noise_intensity` ("Noise level under which all peaks are considered to be likely noise… If not specified, the noise intensity is detected automatically"), `trace_max_mass_deviation`/`align_max_mass_deviation` (`Deviation`), `align_max_retention_time_deviation`, and `min_snr` ("Minimum ratio between peak height and noise intensity for detecting features").
- The top-level README (`external/sirius-client-openAPI/client-api_python/README.md:154-159`) states the same distinction in prose: *"Import [preprocessed](./generated/docs/ProjectsApi.md#import_preprocessed_data) data or [mzML](./generated/docs/ProjectsApi.md#import_ms_run_data) runs,"* using the pre-picked `Kaempferol.ms` file ("three MS2 and one MS1 spectra forming one feature") as the example for the preprocessed path — i.e. the file already *is* a feature; SIRIUS does not detect it.
- Required per-spectrum fields for the MGF path, cross-checked against `external/ms2mol-evaluation/src/ms2mol_evaluation/tools/sirius.py:53-60` (`SiriusEvaluation._add_required_metadata_for_sirius`, which sets `ms_level=2`, `formula=None`, `precursor_formula=None`, `feature_id=<identifier>`, `charge="1+"`, `pepmass=<precursor_mz>` on each matchms `Spectrum` before writing MGF via `save_as_mgf`): `charge` and `pepmass` (precursor m/z) are the two fields this sibling project treats as mandatory MGF header fields for SIRIUS import; `feature_id` is used to map SIRIUS's `mappingFeatureId` output column back to the source identifier (see `SiriusEvaluation._create_scores_array`). Note this sibling project drives SIRIUS via **CLI subprocess** (`sirius --input <mgf> --output …`), not the PySirius `import_preprocessed_data_as_job` call — the metadata-shaping pattern (charge, pepmass, feature_id) is transferable, but the actual call mechanics differ.
- Constraints observed: no explicit "max spectra per project/import call" limit is documented in the generated client docs or README for `import_preprocessed_data_as_job`; the ms2mol-evaluation CLI path self-imposes a chunk size of 30,000 spectra per MGF file (`external/ms2mol-evaluation/src/ms2mol_evaluation/tools/sirius.py:38` `chunk_size = 30000`), which is a pragmatic choice by that project rather than a documented PySirius/API hard limit — **flagged as uncertain**: no source in this repo's reference material states an actual API-side cap.

**Uncertainty / gap:** no doc sentence in the local reference material states in so many words "the ms/mgf/cef/msp import path never performs peak-picking." The conclusion above is inferred from (a) the absence of any noise/SNR/mass-deviation parameters on `import_preprocessed_data_as_job`'s signature, (b) the presence of exactly those parameters only on the mzML path, and (c) the README's own worked example describing the MGF/`.ms`-equivalent input as "already preprocessed" data that "contains three MS2 and one MS1 spectra forming one feature" (i.e., feature boundaries are already given, not detected). A web search for SIRIUS/PySirius official documentation beyond what's vendored in this repo (e.g. an explicit "ImportMsRunDataJob" architecture doc) was not performed as a separate step because the vendored generated-client docs and README already gave a directly-citable, unambiguous parameter-level distinction; if a future ticket needs SIRIUS's own conceptual documentation (v6 docs at `https://v6.docs.sirius-ms.io/`, linked from `external/sirius-client-openAPI/README.md`) to corroborate this in prose, that site was not fetched here.

## 3. Output shape parity (structure-candidate schema vs. import path)

**Finding: the structure-candidate schema returned to callers is fixed by the API endpoint/model, not by the import path — `get_structure_candidates` always returns `List[StructureCandidateFormula]` regardless of whether the underlying `AlignedFeature` originated from an mzML run (`import_ms_run_data`) or from a pre-picked MGF (`import_preprocessed_data_as_job`), because both paths converge on the same `AlignedFeature`/project storage model before any identification job or result API runs. However: the structure-candidate response itself does NOT carry ion mass — ion mass is a field on `AlignedFeature`, not on the structure-candidate object — which contradicted this repo's `CONTEXT.md` glossary as originally written; that glossary entry has since been corrected (see below).**

- `Sirius.get_structure_candidates()` (`external/metabolite-annotator/src/metabolite_annotator/tools/sirius/sirius_config.py:104-126`) calls `self.api.features().get_structure_candidates(project_id, feature.aligned_feature_id)` per feature and converts each returned object with `.to_dict()`.
- The generated docs confirm the return type of `FeaturesApi.get_structure_candidates` (endpoint `GET /api/projects/{projectId}/aligned-features/{alignedFeatureId}/db-structures`) is `List[StructureCandidateFormula]` (`external/sirius-client-openAPI/client-api_python/generated/docs/FeaturesApi.md`, "get_structure_candidates" section, "### Return type" → `[**List[StructureCandidateFormula]**](StructureCandidateFormula.md)`), and the model's own field list (`external/sirius-client-openAPI/client-api_python/generated/PySirius/models/structure_candidate_formula.py:29-42`) is: `inchiKey`, `smiles`, `structureName`, `structureSvg`, `dbLinks`, `spectralLibraryMatches`, `xlogP`, `rank`, `csiScore` (the CSI:FingerID score), `tanimotoSimilarity`, `mcesDistToTopHit`, `fingerprint`, `molecularFormula`, `adduct`, `formulaId`. **There is no `ionMass` field on `StructureCandidateFormula`** (nor on the sibling model `StructureCandidateScored` used by the deprecated `get_de_novo_structure_candidates*`/`get_structure_candidates_by_formula*` endpoints, `external/sirius-client-openAPI/client-api_python/generated/PySirius/models/structure_candidate_scored.py:37-42`, which has the identical field set minus `molecularFormula`/`adduct`/`formulaId`).
- Ion mass (`ionMass`, described as "Mass-to-charge ratio (m/z) of the precursor ion of the feature") is a field on the **`AlignedFeature`** model instead (`external/sirius-client-openAPI/client-api_python/generated/PySirius/models/aligned_feature.py:36`, `52`), obtained via `api.features().get_aligned_features(...)` / `get_aligned_feature(...)`, a separate call from `get_structure_candidates`. `Sirius.get_structure_candidates()` in `sirius_config.py` does call `get_aligned_features(..., opt_fields=[AlignedFeatureOptField.TOPANNOTATIONS])` in the same loop and joins `feature.external_feature_id` (and NPC-compound-class fields via `_add_npc_metadata`) onto each structure-candidate row — but it does **not** currently join `feature.ion_mass` onto the row. So today's `get_structure_candidates` output DataFrame in this codebase's dependency (`metabolite_annotator`) carries `feature_id` + NPC metadata but not ion mass, even though `AlignedFeature.ion_mass` is available and could be joined the same way.
- `AlignedFeature`'s property list (`aligned_feature.py:52`: `alignedFeatureId, compoundId, name, externalFeatureId, ionMass, charge, detectedAdducts, rtStartSeconds, rtEndSeconds, rtApexSeconds, quality, hasMs1, hasMsMs, msData, topAnnotations, topAnnotationsDeNovo, computing, computedTools, qualities, tags`) contains **no field indicating the import source/format** (no `importFormat`, `sourceType`, etc.). This is the structural basis for the parity claim: nothing in the `AlignedFeature` or `StructureCandidateFormula`/`StructureCandidateScored` model definitions varies by import path — an `AlignedFeature` produced via `import_preprocessed_data_as_job` (MGF) and one produced via `import_ms_run_data` (mzML) are indistinguishable objects to every downstream API (`get_aligned_features`, `get_structure_candidates`, `get_structure_candidates_page`, etc.), so the *shape* of results is identical regardless of import path. `feature_import.py:31` (the `FeatureImport` model used by the separate, unrelated `add_aligned_features` JSON-based import endpoint) requires `ion_mass: float` and `charge: StrictInt` as mandatory fields at import time — further evidence that `ionMass`/`charge` are input-time properties of a feature record, not properties SIRIUS computes only for mzML-derived features.

**Resolution applied:** `CONTEXT.md` originally defined *Annotation* as "One feature–structure-candidate pair together with its CSI:FingerID score and ion mass — the row unit returned by `get_structure_candidates`," implying ion mass is native to that call's return row. Per the model definitions found here, it is not — ion mass must be joined in from a separate `AlignedFeature` object (which `sirius_config.py`'s current implementation fetches in the same loop but does not currently attach to the row). `CONTEXT.md` has been corrected: *Structure candidate* now states it carries only the CSI:FingerID score, and *Annotation* now describes ion mass as joined in from the feature by feature id. Which pipeline code performs that join (and whether it mirrors or extends `sirius_config.py`'s existing per-feature loop) remains a downstream design decision, out of scope for this research ticket.
